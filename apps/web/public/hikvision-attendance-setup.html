1. Why a bridge is needed

JambaHR already ships a device punch endpoint — POST /api/attendance/punch — that records attendance from any hardware. But the Hikvision terminal cannot call it directly, for two reasons:

ObstacleDetail
Payload mismatch The terminal emits events in Hikvision's own format (fields like employeeNoString, serialNo, time, currentVerifyMode). JambaHR expects { employee_code, timestamp, event_type }. Hikvision's HTTP-Host config has no field to add an Authorization: Bearer header, which the endpoint requires.
Network reachability The terminal sits behind your office router (private IP). JambaHR runs in the cloud and cannot reach into your LAN. Exposing the Hikvision device to the public internet is a serious security risk and must never be done.

The fix is a tiny always-on bridge (relay) service running on your office network. It sits between the device and JambaHR: it receives the device's raw event, translates it, attaches the secret token, and forwards a clean punch to JambaHR over HTTPS.

What already exists vs. what to build

Already built in JambaHR: the /api/attendance/punch endpoint, the Settings → Fingerprint configuration screen (enable toggle, webhook URL, device token, per-employee device codes), the source = 'device' attendance tag.

You build once: the bridge service (~150 lines of Node.js/Python, or an off-the-shelf middleware). It is the only new moving part.

Two integration mechanisms matter here, both over ISAPI (Hikvision's HTTP/REST API):

  • Push (event listening): the device POSTs each event to an HTTP Host you configure (IP + port + JSON). Great for real-time; needs a listener always reachable on the LAN.
  • Pull (polling): your service periodically queries /ISAPI/AccessControl/AcsEvent for new events using Digest auth. More resilient to brief downtime; you control the cadence.

The bridge can use either. Push is recommended for simplicity and immediacy; pull is the robust fallback if your network drops pushes.

Cloud-only alternative (enterprise)

If you run HikCentral Professional or use Hik-Connect, the device can register outbound over ISUP 5.0 and you can consume events via Hikvision's OpenAPI in the cloud — no on-site bridge. This adds platform licensing/complexity and is usually overkill for a single SMB office. The LAN-bridge approach above is the recommended path.

5. Employee-number mapping (the key concept)

Every person enrolled on the Hikvision device has an Employee No. (Hikvision calls it employeeNo / employeeNoString). Every JambaHR employee has a Device Code (employees.device_code). These two must be identical for each person.

On the Hikvision deviceIn JambaHRResult
Employee No. = EMP001Device Code = EMP001✅ Punch resolves to that employee
Employee No. = 1042Device Code = 1042✅ Works — any consistent scheme is fine
Employee No. = EMP001Device Code blank, email matches⚠️ Falls back to email match if your bridge sends email instead
Employee No. = 99No employee with Device Code 99❌ Endpoint returns 404 "Employee not found"

Recommendation: pick one scheme up front (reusing each person's existing staff ID is cleanest) and use the same value in both systems. Set Device Codes in JambaHR under Settings → Attendance → Fingerprint → Employee codes table.

Part A · 10 minutes

6. Set up the JambaHR side

1

Enable Fingerprint integration

Go to Settings → Attendance → Fingerprint. Toggle Enable fingerprint punch-in on.

2

Copy the Webhook URL & generate a Device Token

The webhook URL is https://jambahr.com/api/attendance/punch. Click Regenerate token to create a secret like dt_xxxxxxxx… and copy it. The bridge will send this as Authorization: Bearer dt_…. Keep it secret; regenerating invalidates the old one immediately.

3

Set each employee's Device Code

In the Employee codes table, enter the same ID you'll use as the device's Employee No. for each person (see §5). Save each row.

Part B · 30–45 minutes

7. Set up the device

1

Power, network, first boot

Mount and power the terminal, connect Ethernet, set the device admin password on first boot. Give it a reserved IP on your router.

2

Set time zone & NTP

Set the device to IST (UTC+5:30) and enable NTP. Accurate time matters — JambaHR rejects punches whose timestamp is more than 24 hours off server time.

3

Enroll people (with matching Employee No.)

Add each person in iVMS-4200 (or on-device): capture face / fingerprint / card and set their Employee No. to exactly the Device Code you set in JambaHR. Enroll on-device for best face-template quality.

4

(Optional) Enable Attendance Mode

Turn on the terminal's attendance status feature so staff tap Check In / Check Out. The event then carries an explicit status, letting the bridge send event_type: "clock_in" / "clock_out" precisely. If you skip this, JambaHR auto-toggles (see §9).

5

Point the device at the bridge (push mode)

In the device's event/notification settings (via iVMS-4200 or the device web UI), configure the HTTP Listening / Notification Host:

  • IP / host: the LAN IP of your bridge machine
  • Port: the port your bridge listens on (e.g. 8080)
  • Protocol: HTTP · Format: JSON
  • URL/path: e.g. /hik-events

The device will now POST every access event to your bridge.

Part C · build once

8. Build the bridge

A minimal Node.js receiver that accepts Hikvision events and forwards JambaHR punches. Host it on the always-on LAN machine (run under pm2 / a systemd service / Docker so it restarts on boot).

// bridge.js  —  Hikvision → JambaHR relay (push mode)
import express from "express";

const JAMBA_URL   = "https://jambahr.com/api/attendance/punch";
const DEVICE_TOKEN = process.env.JAMBA_DEVICE_TOKEN; // the dt_… from Settings
const seen = new Map(); // debounce: employeeNo → last punch ms

const app = express();
app.use(express.json({ limit: "5mb" }));
app.use(express.text({ type: "*/*", limit: "5mb" })); // some firmware sends multipart/text

app.post("/hik-events", async (req, res) => {
  res.sendStatus(200); // ACK fast — device retries on timeout

  const body = typeof req.body === "string" ? safeParse(req.body) : req.body;
  const ev = body?.AccessControllerEvent ?? body?.access_controller_event ?? {};

  // only successful authentications (ignore denied / door / tamper)
  const employeeNo = ev.employeeNoString ?? ev.employeeNo;
  if (!employeeNo) return;                 // not a person event
  if (ev.subEventType && isDenied(ev)) return; // skip failures

  // debounce repeat scans within 90s
  const now = Date.now(), last = seen.get(employeeNo) ?? 0;
  if (now - last < 90_000) return;
  seen.set(employeeNo, now);

  await fetch(JAMBA_URL, {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      "Authorization": `Bearer ${DEVICE_TOKEN}`,
    },
    body: JSON.stringify({
      employee_code: String(employeeNo),    // === employees.device_code
      timestamp: ev.time ?? new Date().toISOString(),
      event_type: mapStatus(ev),            // "auto" | "clock_in" | "clock_out"
      device_id: "front-door",
    }),
  }).catch(console.error);
});

// If using Attendance Mode, map the device's status; else "auto"
function mapStatus(ev) {
  switch (ev.attendanceStatus) {
    case "checkIn":  return "clock_in";
    case "checkOut": return "clock_out";
    default:         return "auto";
  }
}

app.listen(8080, () => console.log("bridge on :8080"));
Pull-mode variant

If you prefer polling, the bridge instead calls POST http://<device-ip>/ISAPI/AccessControl/AcsEvent?format=json with HTTP Digest auth (device admin user/password) on a timer, requesting events since the last seen time. Dedupe on (deviceId, serialNo), then forward each new granted event exactly as above. Use this when pushes are unreliable.

Verify against your firmware

Exact event field names and the menu path for HTTP Listening vary by firmware version. Confirm the real payload by logging the first few requests your bridge receives, then adjust the field extraction (employeeNoString, time, attendanceStatus) accordingly before go-live.

9. Clock-in vs clock-out

By itself a punch is just "access granted." Two ways to decide in vs out:

ApproachHow it worksTrade-off
Attendance Mode (recommended) Staff tap Check In / Check Out on the terminal. Bridge sends explicit event_type. Supports breaks & OT statuses too. Requires staff to pick the right button.
Auto toggle Bridge sends event_type: "auto". JambaHR clocks in if there's no open record today, else clocks out. First punch = in, second = out. A 3rd punch the same day flips back to "in" — fine for simple single-shift offices, less so for multiple in/out per day.

10. Things to note

  • Cloud can't reach your device. That's by design — the bridge is the only thing that talks to both sides. Never port-forward the Hikvision device to the internet.
  • Timestamps are validated. Punches more than 24 h from server time are rejected (422). Keep device NTP + timezone correct.
  • Filter to successful authentications only. Devices emit many event types (denied, door open, tamper, card-reader status). Forward only access-granted person events, or you'll create phantom records.
  • Debounce repeat scans. Face re-detection can fire several events seconds apart. The bridge debounces per person (90 s example) so one approach = one punch.
  • One token per org. The current design uses a single device token for the whole organization. Multiple doors share it; use the device_id field to tell them apart in records.
  • Unknown person → 404. If someone is enrolled on the device but has no matching Device Code in JambaHR, the punch is rejected. Keep the two enrollment lists in sync.
  • Capacity is ample. 3,000 of each credential type comfortably covers a 10–500 employee office.
  • Overnight shifts. JambaHR's attendance treats a record per calendar day; overnight handling has known limits. If you run night shifts, validate the day boundary behaviour before relying on device punches for payroll.

11. Security

Never expose the device to the public internet

Hikvision access terminals are a frequent target of disclosed vulnerabilities. Keep the device on the LAN (ideally a separate VLAN), behind your firewall, never port-forwarded.

  • Change the default admin password to a strong, unique value on first boot.
  • Keep firmware updated — apply Hikvision security updates promptly.
  • Protect the device token. Store dt_… in the bridge's environment, not in code or logs. Regenerate it in JambaHR if leaked (old token dies instantly).
  • Lock the bridge's listener to accept connections only from the device's IP; the bridge's only outbound destination is jambahr.com over HTTPS.
  • Disable Hik-Connect cloud on the device if you're not using it.
  • Biometric data stays on the device. JambaHR only ever receives the Employee No. + timestamp — never face/fingerprint templates. Make sure your staff consent + data-retention policy covers the on-device biometrics.

13. Go-live checklist

  • Attendance module enabled for the org
  • Fingerprint integration toggled on; device token generated & copied
  • Device Codes set for every employee in JambaHR
  • Device powered, on LAN, reserved IP, admin password changed
  • Device timezone = IST, NTP enabled
  • People enrolled with Employee No. = their JambaHR Device Code
  • (Optional) Attendance Mode enabled for explicit in/out
  • Bridge deployed on always-on LAN machine, auto-restarts on boot
  • Device HTTP Host points at the bridge
  • Test punch by 2–3 staff → records appear in JambaHR with the "via device" tag
  • Confirmed denied/duplicate events are filtered and debounced
  • Bridge listener firewalled to the device IP only
